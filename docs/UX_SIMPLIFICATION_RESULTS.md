# Coach, parent and supported practice UX simplification

Date: 12 October 2026. Branch: `codex/coach-parent-ux-simplification`; base: `codex/demo-first-entry` at `5f77fe25fe92eeff9a8eca80deea211fe4c2d0a4`.

This implements the five priorities from [LIVE_UX_AUDIT.md](LIVE_UX_AUDIT.md). The earlier audit remains an account of the earlier read-only run; it is not relabelled as an authenticated success. This is an agent-led walkthrough and automated browser verification, not research with real families or coaches. No timing savings or physical-device validation are claimed.

## Safe environments

Live issue reproduction and read-only after checks: `http://127.0.0.1:3000`, fictional legacy demo. Fresh before/after JPGs are under `screenshots/ux-simplification/`. The original audit evidence is preserved in `screenshots/live-ux-audit/`.

Authenticated tests: separate production QA build `.next-football-qa`, server port 3001, and a fresh guarded `.local/e2e-*.sqlite` database from the repository Playwright configuration. The final build also sets SPORTOZEN_DATABASE_PATH to a dedicated ignored e2e-build database (WAL initialized before parallel build workers) and BETTER_AUTH_URL to port 3001. An intermediate build without that database override hit a SQLite lock; no database was reset. Existing registration, academy creation and manual invitation/acceptance APIs establish fictional owner, coach and parent accounts. Browser contexts use their own test authentication; no customer cookies or demo role selector establish authority. Training tests also establish an unrelated fictional academy and child. These APIs prepare fixtures; the training, plan, update and conversation interfaces are tested in the browser. Do not interpret this as every registration/invitation step being manually audited.

No customer database reset, external message/invitation transmission, payment collection or deployment is part of this change. Server membership/guardian/academy scope, report approval, immutable history, version checks and external NOT_SENT semantics remain in place.

## Data and approval boundary

Approval now explicitly leaves an update APPROVED/UNPUBLISHED. The separate **Share in parent app** action (`publishUpdate`) rechecks current staff scope, version, approved source eligibility and eligible guardians/preferences transactionally; external delivery stays NOT_SENT. A parent Message coach action opens or creates a private conversation linked to that published update, with the relation checked server-side. Existing API consumers that previously relied on approveUpdate to publish must call publishUpdate explicitly.

No new performance scoring or child-role model was introduced. Report activities can now carry optional `cue` and `drillId` captured from the already-authorized assigned drill/session snapshot when a report is approved. The existing report rendering and PDF layout are preserved. Old snapshots remain immutable and may lack those new optional fields.

Practice feedback is labelled **Parent-submitted practice feedback** and stored only when intentionally submitted through existing conversation services. It does not create evidence, mark a drill complete, change a plan, or convert difficulty into poor performance. Draft text stays in component/provider memory; no private message body is placed in a URL or read directly from browser storage. Native navigation confirms unsaved changes; failed saves keep their editor state. Persisted records and conversation replies survive refresh; unsaved drafts are not claimed to survive a browser crash. Legacy observation/session creation now also checks the storage result before clearing or navigating. The injected-quota regression tests objective, observation and session drafts separately. Training retries retain their existing request receipts; no global idempotency guarantee is claimed for all older conversation mutations.

Parents continue to receive only server-authorized linked-child approved records and their own conversations. Restricted staff notes remain excluded by the service projection, not merely hidden CSS. Selecting a demo role remains explicitly fictional; authenticated role still comes from membership. WhatsApp/email/SMS/push remain disconnected and external delivery stays NOT_SENT. No provider credentials, medical recommendations, rankings or comparisons were added.
