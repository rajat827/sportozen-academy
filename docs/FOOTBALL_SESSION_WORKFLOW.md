# Authenticated football training workflow

Feature branch: `codex/football-session-evidence-workflow`, based on `codex/football-only-release` (`e99ebd98f03a5af23c245923c849daef3a47ca35`). No newer relevant remote branch existed at the starting inspection. This extends the current authenticated workspace; legacy demonstration routes are not part of acceptance.

## Reproduce with synthetic accounts

1. Register separate fictional owner, coach and parent accounts at `/sign-in`. Create an empty football academy. Use manual invitation tokens in Settings to give the coach membership. Add two fictional players assigned to that coach. Verify the intended guardian before linking the parent to only the first player.
2. In Settings create a branch with a valid IANA time zone. In Development copy an existing curriculum drill, create each player's ACTIVE plan, choose focus, reason, drill, observation criteria, optional safe practice and review date. Private working notes remain staff-only.
3. Owner opens **Training**, creates a named squad with explicit player membership and a venue under the branch. Historical player squad labels are not silently converted into membership.
4. Coach opens **Training**, chooses the squad/venue, recorded location, assigned coaches, dated start/end and ordered drills/durations. Save the draft. Times use the branch's zone, independently of the browser. Spring DST gaps and autumn ambiguous local times are rejected; choose another wall time. No recurring engine is provided.
5. Open **Session Desk → Objectives**. Give each player a distinct goal, assigned drill, personal cue and observation criteria. The link must match that child's current plan where one exists. A missing plan is clearly labelled and an explicit unlinked objective is allowed. The session keeps the objective and roster snapshots when the current plan or squad later changes.
6. Schedule the session and start training. **Attendance** begins UNMARKED for every expected player. Mark individually or use Mark all present, then save. Corrections to an already marked status need a reason. The authorised audit-history link shows each version and actor. Unmarked is never absent; no historical seeded percentage is used.
7. **Agenda** displays ordered drill snapshots, durations, purpose and coaching cues. Select the current drill for the desk view. This navigation selection is transient; the saved evidence identifies the drill actually recorded.
8. **Evidence** records a player, session drill and historical objective/plan link, observation, course/target/conditions, collection method, visibility and separate staff-only note. Choose observation only, successful/recorded attempts, or elapsed seconds. Negative/impossible results are rejected. Zero attempts explicitly means no measurement, never a 0% skill score. There is **No video attached**; no animation or AI analysis is a player-performance source.
9. **Review** requires explicit verification before REVIEWED, UNCLEAR or REJECTED. Reviewed content cannot be edited in place. Capture new evidence; a staff/API supersession preserves the historical version. Comparison eligibility requires the same child, drill version, conditions, method, unit and measurement plus reviewed status; no improvement claim is generated automatically.
10. Against reviewed evidence, update the plan's next step. Resolve stale-version conflicts by reviewing the unsaved draft against the reloaded state. Complete the session only after attendance is marked and outstanding evidence is reviewed or classified.
11. From **Review**, prepare a report using parent-eligible reviewed evidence from that completed session. In **Reports**, inspect the source player, session, observation, drill version, conditions, date and attendance; verify and approve. The existing premium preview and PDF share the approved snapshot. Staff-only evidence notes and other players are excluded.
12. In **Messages**, select **Reviewed session update**, select that approved report, prepare/edit a draft, submit, verify and approve. **Upcoming training update** instead describes the approved plan's intended work and explicitly says planned activities are not completed results. Approved message and source versions are retained in approval history. Editing returns an update to draft/unpublished and requires new review. External delivery is always **NOT_SENT**.
13. Parent signs in separately, sees only the linked child's approved plan/report/update, downloads the private PDF, and uses the existing private conversation/reply composer. Attendance correction requests are questions to staff; parents cannot write the attendance ledger. Coach responds; internal notes never enter the parent projection.

## Persistence and reliability boundary

UI → `useWorkspace` → authenticated training application service → existing repository interface → SQLite adapter. Components do not read browser storage. New record kinds are `squad`, `venue`, `session`, `attendance`, `evidence`; all carry academyId, football sportId, record version, updated actor/time. Sessions snapshot roster names, objectives and drill bodies/versions. No squad changes rewrite historical sessions or attendance.

`POST /api/workspaces/[academyId]/training` uses authenticated current membership, enabled module, football scope, coaching assignment and player relationships. Every command has a UUID requestId. Identical retries return the original receipt after current access is rechecked; reusing a key with different content returns 409. Saves, history, audit and receipt are one BEGIN IMMEDIATE transaction. Updates require the expected record version. Attendance uses deterministic session/player IDs and version-checked entries; a failing entry rolls back the entire bulk action. Reviewed data cannot be silently overwritten. Workspace plan-editor saves and evidence-based next-step edits also check versions; older API callers without an expectedVersion retain their compatibility boundary, which is not a global concurrency guarantee for all legacy features.

New reads use the existing authorised record APIs; parents/support receive no raw squad, session, attendance or evidence records. `GET .../training?kind=attendance&id=...` and other training kinds expose version history only to authorised staff. Coaches must be assigned to the session and authorised for every roster player; changing a player's coaching assignment can restrict the prior coach's access without deleting history. Owners/admins retain the academy audit. Reports and parent inbox use immutable approved projections, not raw training records. Cross-academy relationships, membership revocation and cancelled-session writes are checked server-side.

Migration 002 is additive: `src/server/migrations/002-football-training.ts` creates request receipts and version history and raises user_version to 2 without downgrading later versions. Existing record storage needs no column changes. It never imports browser demo data, rewrites historical labels, drops records or resets the customer database. Rollback: deploy the prior code while retaining the new tables/record kinds and approved snapshots; older workspace lists ignore the extra kinds. Before any production rollout/rollback, take and validate an operator-controlled consistent SQLite backup including WAL state. Do not delete the new records to roll back; retain them for a forward migration. No rollback/reset was run on customer data.

## Verification and limitations

Run the configured five gates. With an app already running, set `SPORTOZEN_QA_BUILD=1` for build and E2E. QA owns port 3001 and guarded `.local/e2e-*.sqlite`; the controlled restart uses only its own port 3002 process. Port 3000 and its served assets are preserved. Screenshots and actual PDF exports: `docs/screenshots/football-training/` at 1440/768/390/320. See QA_REPORT.md for exact final results.

Scope is a **supervised synthetic-data pilot using coach-recorded evidence**. Real child-data deployment still requires secure account recovery/ownership, staff MFA, verified guardians and consent, retention/deletion, durable backup/monitoring, managed multi-instance storage and independent security review. Video upload, automatic AI analysis, recurring schedules, payment collection and external messaging are outside this task. The existing P2 long-report continuation branding issue remains open unless separately visually fixed; text extraction alone does not resolve it.
