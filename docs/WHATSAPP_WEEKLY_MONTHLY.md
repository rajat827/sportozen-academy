# Weekly plans, monthly reports and WhatsApp operations

This extends authenticated `/workspace` workflows. Legacy owner/coach/parent routes remain fictional browser demonstrations. Payments and AI video analysis are outside this feature. AI Video Analysis is Coming soon.

## Content and approval

Training → Prepare weekly plan selects a squad and Monday. Confirmed scheduled sessions, historical objectives, academy drill snapshots and the active personal plan prefill individual drafts. Missing schedules, activities, focus or observation criteria block approval. Coaches can record personal wording and optional safe practice with one save. Preparing a week requires no report, video or retrospective evidence. Each child needs individual source/recipient review and approval. In-app publication is a separate action, filtered through current guardian membership and child relationships. Notification preferences independently control WhatsApp, and private publication must precede dispatch.

Upcoming updates additionally accept `sourceWeeklyPlanId`; report-backed updates retain their existing behavior. A weekly source is an independently approved snapshot, represented as planned activities rather than completed achievements. Parent payloads never include private plan notes. `weekly` records retain author, reviewer, approval time, source versions and explicit period boundaries. Edits clear approval and cancel pending delivery; all plan/session writers invalidate affected pending snapshots through the existing repository. Issued content remains historical. Prepare deliberate correction creates a separate draft linked to the issued version, requiring new individual review.

Reports → Prepare monthly reports uses the academy IANA timezone and inclusive-start/exclusive-end boundaries. Only completed roster sessions and reviewed parent-eligible observations recorded within the period enter the model. Cancelled/unfinished sessions are excluded. Attendance shows present, absent, excused and unmarked separately; its denominator is present + absent, with no percentage when this is empty. There are no cross-child comparisons or inferred improvement. Missing sources remain missing. Each source observation includes recording conditions and provenance, and is not treated as comparable just because it shares a drill label.

Monthly drafts reuse the existing report approval, immutable approval history, private guardian projection, ReportViewModel and premium PDF renderer. Source fingerprints are rechecked at approval; final monthly approval waits until the local reporting month has ended. New attendance, completed sessions or eligible evidence after approval withhold the notification until a reviewed correction is prepared, preserving the original PDF. Read-only history aggregates only the authorised child, including their recorded participation when another roster player changes coach. Source/commentary edits are reviewed before approval; regeneration cannot overwrite an approved historical report. Repeated preparation returns the existing player/month draft or report. Reviewed monthly corrections are explicit separate records. Commentary, sources, attendance basis and next priorities are the same in the parent screen and PDF. Preparation/download never enqueue or send externally. Notifications contain a sign-in-protected workspace link, with no credentials or public PDF URL.

## Configuration and external blockers

No real send or deployment was authorised during implementation. Schedules and sending start disabled. Each academy must configure:

1. Its own registered Meta WhatsApp Business Account and connected Cloud API phone-number ID, with applicable account eligibility and permissions (`whatsapp_business_messaging`, `whatsapp_business_management`). No account/category/pricing approval is assumed.
2. A server environment credential reference `SPORTOZEN_WA_<ACADEMY_KEY>` containing JSON fields `academyId`, `phoneNumberId`, `wabaId`, `token`, `appSecret`, `verifyToken`, and `graphVersion`. IDs must exactly match that academy's saved settings. Tokens never go to the browser or persisted application records. Use an operator-managed secret store/environment; never commit this JSON with real values.
3. Two Meta-approved, body-only positional templates in `en_GB`. Local draft definitions are in `src/services/communication/whatsapp-templates.ts`; supply representative synthetic example values when submitting them to Meta. Proposed category is UTILITY, subject to Meta's review/reclassification. Configure their actual provider names. Verification checks exact approved body, language and status; a local draft is not provider approval. Supported parameter/body budgets are deliberately conservative: single-line nonempty parameters ≤400 characters and rendered body ≤1024 characters. Full monthly reports remain private. Broader languages/media/buttons require an explicit adapter extension and provider review.
4. A publicly reachable HTTPS callback `/api/whatsapp/<academyId>` subscribed to that WABA's `messages` events. GET verifies the configured token and returns `hub.challenge`; POST validates `X-Hub-Signature-256` as raw-body HMAC SHA-256 with constant-time comparison, then checks both WABA and receiving-phone identity. Signed events persist before acknowledgement and are processed by the worker. A 1 MiB request limit applies. Deployments, callback provisioning and subscriptions were not performed by this change.
5. A verified guardian-to-phone relationship with a documented verification reference and explicit academy-named opt-in/consent evidence, plus weekly/monthly category preferences. Parents may manage their own preferences and opt out, but cannot self-certify contact verification. STOP, UNSUBSCRIBE and OPT OUT text events cancel pending notifications. Staff must also record opt-outs received elsewhere. No groups are supported.

Settings exposes Not configured, Awaiting provider/template setup, Ready for controlled testing, Connected and Configuration error. Populated fields alone do not make a sender ready. The Verify action only reads provider configuration; each dispatch verifies sender/templates again. TEST mode additionally requires a server recipient allowlist. Sender identities cannot be shared accidentally between academy settings; secrets independently bind academy, WABA and phone.

Business-initiated notifications always use approved templates. An intentional staff WhatsApp reply is allowed only within 24 hours of the verified contact's most recent inbound event; it rechecks that window at dispatch. Outside that window staff respond in-app. In-app replies do not auto-send. No autonomous coaching bot or proactive response to unknown contacts exists.

## Persistent worker and schedules

Use the same SQLite file and server environment as the web app on one host:

```sh
pnpm communication:worker
pnpm communication:worker --once
```

The command loads local environment files when present and runs with the Node `react-server` export condition and tsx path resolution. Run it as a supervised background service with automatic restart, limited filesystem access, a protected environment, log capture and shutdown signaling. One tick processes up to 100 signed events, prepares configured due monthly drafts/reminders, identifies due approved notifications, and claims at most one delivery. The loop sleeps ten seconds between ticks. It is independent of browsers/web requests, and does not introduce another database or Redis.

Settings defines reporting timezone (must match academy), planning lead days, preferred weekly sending day/time, monthly draft and notification days/time, quiet hours and pause/resume. Monthly output concerns the previous completed month. Weekly output concerns the next Monday, selecting the following Monday when run on Monday. Sending days are resolved at/before the configured planning lead date. Ambiguous DST folds/gaps create an internal scheduling reminder rather than guessing. Quiet hours use the declared reporting zone and defer fifteen minutes, subject to expiry; parent quiet hours are also enforced. `Awaiting coach approval` reminders are internal and never approve or invent content. Defaults are disabled and paused.

Missed weekly runs catch up only within 24 hours of their due time and before the training week starts. Expired weekly messages are cancelled, never blasted after an outage. Monthly notifications expire at the end of the following notification month. No historical backlog is generated beyond the previous completed month. Deliberate reviewed corrections can be queued explicitly; an in-week weekly correction includes only confirmed sessions remaining when prepared and expires at the week end. A schedule change cancels affected queued weekly messages immediately and requires source review; delivered history never silently changes.

Claims, attempts, job state, provider IDs and signed events are durable. Each POST attempt freezes its recipient, consent reference, sender binding and exact template parameters/body without storing tokens, so signed receipts still match that attempt after a guardian changes phone. Claims are committed before network calls; no transaction is held across provider requests. A claim interrupted for two minutes becomes UNKNOWN and needs reconciliation, never an automatic resend. Confirmed transient rejections use bounded exponential backoff; ambiguous timeouts or malformed acceptance receipts become UNKNOWN. Provider events can reconcile a job by receipt or its opaque job correlation ID after a persisted attempt. There is no exactly-once external guarantee.

The scheduled deduplication key is academy + player + guardian + WhatsApp + output type + period, with a separate explicit correction key. Reapproval can rebind an unattempted cancelled job but cannot create another normal period send. Each guardian has separate results. PROVIDER_ACCEPTED is not SENT/DELIVERED/READ. Those stronger states require signed provider evidence, and delayed statuses cannot regress READ/DELIVERED. FAILED/UNKNOWN/CANCELLED remain visible separately from immutable content. Monitor UNKNOWN, unmatched events, aged queues and worker heartbeat; investigate provider evidence before any operator correction, rather than clearing a claim and resending.

## Parent replies

Receiving sender identity and verified academy contact determine the guardian. A referenced outbound receipt identifies the child only if the guardian still has that child's relationship. With one eligible child an unthreaded reply can route to the existing private conversation. Multiple eligible children without usable context produce AMBIGUOUS_CHILD for staff clarification; an Owner/Admin must confirm the child with the parent and deliberately attach the event. Unresolved message text is restricted to those coordinators. Unknown or revoked referenced receipts never fall back to guessing a single child. Unknown/unverified senders receive no player information. Text replies carry a WhatsApp channel label. Unsupported media is recorded for staff handling; media download and automatic transcription are not implemented. A staff in-app response remains in-app unless its explicit WhatsApp action is selected and permitted.

Do not run this during development or CI. Obtain explicit permission for the particular staging test recipient/content. Confirm synthetic content, verified linked test guardian/opt-in, Meta-approved exact templates, sender verification and signed webhook subscription. Configure `SPORTOZEN_WHATSAPP_TEST_RECIPIENTS` as a comma-separated E.164 allowlist in the server environment, keep mode TEST, and enable `SPORTOZEN_WHATSAPP_SEND_ENABLED=true` only for the controlled window in a supervised `NODE_ENV=production` staging worker. LIVE also requires `SPORTOZEN_WHATSAPP_LIVE_ENABLED=true`. CI and every non-production NODE_ENV block real adapter sends. Never put real parent numbers in fixtures or examples. Review exact template rendering/recipients, queue one approved test notification, run the worker and inspect acceptance then signed delivery status independently. Restore the sending flag to false afterward. Passing transport doubles is not phone delivery.

## Migration, rollback and readiness

Parent language preferences outside English are withheld until an explicitly approved translated adapter/template exists. Sender rotation needs a supervised drain/reconciliation: newly received webhooks must match the current WABA/phone. Already persisted status events can reconcile their frozen attempt, but there is no retired-sender credential registry.

The inherited Next build warning about dynamic SQLite path tracing still needs a production packaging audit. Inspect the deployment bundle to exclude local databases, credentials and QA artefacts before any release; no deployment was performed here.

Migration 003 adds settings, contacts, per-recipient jobs/attempts, events and reminders, preserving current records and IDs. Weekly snapshots use the existing workspace record store and version history. No existing database was reset or replaced. Before production rollout take and verify an operator-controlled consistent SQLite/WAL backup. Rollback code while retaining added tables/kinds and all historical snapshots/events; never delete communication data to roll back. Stop/pause the worker and disable sending before rollback. Older code ignores new record kinds; forward migration can resume retained work.

Production still needs managed credential rotation, approved templates/account verification, staging callback delivery tests, supervision/monitoring/alerts, backup recovery drills, retention/deletion policy for phone/consent/webhook text, verified guardian processes and the existing account-recovery/MFA/security work documented in SECURITY_AND_DEPLOYMENT.md. Single-host SQLite is intentional; multi-instance deployment requires a demonstrated storage/worker strategy. No live WhatsApp test, commercial activation, purchase or deployment is implied by local verification.
