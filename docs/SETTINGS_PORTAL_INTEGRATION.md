# Authenticated Academy Settings

The authenticated Settings page uses the academy portal shell and the actual academy-scoped `useWorkspace` controller. It does not import the preview adapter, fictional fixtures, preview shell, or browser-storage persistence. The visual source remains `docs/reference/approved-ui/settings-screen.png`; its profile/contact/preferences/venues column and logo/plan/danger column determine the composition. Actual authorised records determine text, logos, subscription metadata and venues.

## Configuration save

`use-academy-settings.ts` stages profile, contacts, PNG branding, regional display preferences and module configuration in one draft. Both logo previews share the same staged value; staging a file does not write to the server. PNG files must be under 200 KB. JPG is explicitly unsupported by the existing configuration contract.

The single Save Changes action validates the shared schema, sends the draft's original `expectedVersion`, and shows success only after the service confirms the saved academy/version. The server reloads current membership and current configuration inside the transaction, compares the expected version, uses an atomic conditional update, and reads the stored record back. Failed requests and conflicts retain the entered draft. A conflict review exposes the current saved configuration and logo; applying the reviewed version requires an explicit choice. Keeping a draft means its fields will be applied on the next save.

Unsaved drafts recover in module memory across same-document Back/Forward navigation, scoped by academy and authenticated user. Explicit discard and a confirmed save clear recovery. Ordinary navigation and full reload retain the existing unsaved-change confirmation. No private draft is written to a URL, localStorage or sessionStorage.

Legacy configuration JSON reads with compatible defaults: version 0, Monday week start, DD MMM YYYY date display and 12-hour time display. A default timezone change does not rewrite branch timezones, recorded local session times, resolved instants, historical rosters or report snapshots. New academies enable the fees module and its initial entitlement. Existing academies keep their recorded module selection and entitlements until an authorised configuration action; module controls do not grant subscription entitlements.

## Connected workflows

- Academy: actual profile/contact/branding/preferences/module configuration; actual venues and zone resources through the versioned training command.
- Team: current memberships, authorised manual invitation token preparation, and confirmed membership revocation. Preparing a token sends no message or email.
- Sessions: existing branch/programme/support-access workflows.
- Notifications and Integrations: existing communication configuration/provider state and parent notification preferences; no simulated WhatsApp delivery. The controller passes a validated selected child into the parent preferences, preserving private dietary/allergy notes and naming the child explicitly.
- Account: current authenticated identity, academy role and existing authentication sign-out.

Subscription information shows the recorded tier/status/modules. Subscription billing management and academy deletion have no supported action, so their controls remain disabled with explanatory text. Player training fees remain separate from the Sportozen software subscription. A venue's status reads Recorded because the venue model has no active/archive field; the implementation does not invent Active status.

Venue edits use the existing academy/branch/resource checks, version checks and idempotency key. Identical retries reuse the request key. A successful edit does not rewrite historical session snapshots. Owner/admin permissions remain server-authoritative; other roles do not receive the academy administration form or subscription metadata.

## Player model compatibility

Optional age category, birth date, position, status and primary squad ID extend existing player records. Age category remains separate from the legacy batch label. Existing player edits require the record version. A primary batch placement change requires owner/admin permission and explicit review, validates the academy's actual squad, and atomically updates current squad membership with the player. Historical session rosters remain unchanged. A failure rolls the complete operation back.
